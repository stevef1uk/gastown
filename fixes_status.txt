### 83. Polecat formula prompt was 20 KB — small LLMs regurgitated template fragments
- **Symptom (user-reported)**: The polecat created on `testgt2/polecats/rust` produced
  bizarre first turns. Its initial LLM response was 1965 chars with **40+ `CMD:` lines**,
  most of which were template fragments verbatim from the formula:

    ```
    CMD: git add <test files> && git commit -m "test: add failing tests for Implement the solution"
    CMD: git fetch origin git branch -a | grep <branch-from-notes>

    ```
  Unresolved `{{setup_command}}` placeholders, `<angle-bracket>` fillers, missing
  shell operators between commands, and a direct push to `main` (which polecats are
  forbidden to do) all in one LLM response. No real work happened — the model just
  echoed the formula's bash example blocks back as commands.
- **Root cause**: `showFormulaStepsFull` (`internal/cmd/prime_molecule.go`) was dumping
  the *entire* formula description into the polecat's LLM context every time
  `gt prime` ran. For `mol-polecat-work` that is **563 lines / ~20 KB** of prose,
  tables, code fences, and example bash. Small LLMs (e.g. ollama/llama3.3, an 8B-class

          tables to find the first prose sentence).
        - The body of exactly *one* step is inlined in full — the "focus" step,
          marked with `►`. Default focus is step 1, so a freshly-primed polecat
          sees the workflow outline plus detailed instructions for the next thing
          it should do.
        - A footer reminds the model "bash blocks are examples, not commands to
          copy verbatim" and "do NOT emit `CMD:` lines that contain `{{placeholders}}`
          or `<angle brackets>`". The model that ate this prompt actually obeyed
          both rules on the very next turn.
    2. **New `gt prime --step N` flag**: pins the renderer to step N's full body
        so the polecat can drill into the next step without re-receiving the
        whole formula. The renderer plumbing is a single package-level int
        (`formulaStepFocus`) set by `SetFormulaStepFocus(n)` in `runPrime`
        and reset on return.
    3. **Escape hatch**: `GT_FORMULA_VIEW=full` re-enables the legacy verbose
        dump for operators using large models that benefit from the full prompt.
- **Verification**:
    - Unit tests (`prime_molecule_render_test.go`):
        - `TestShowFormulaStepsFull_CompactByDefault` — asserts `mol-polecat-work`
          renders to **3331 bytes** (down from ~20 000), well under the 6 KB

        - `TestShowFormulaStepsFull_LegacyFullMode` — `GT_FORMULA_VIEW=full`

## Fix 97: Orphan `dolt sql-server` processes hanging `gt down` / `gt status`

- **Symptom**: `pgrep -af 'dolt sql-server'` showed 20+ ephemeral

- **Root cause**: `bd` (the beads CLI) spawns its own ephemeral
  `dolt sql-server` on a random port when it can't reach the
  canonical 3307 server (e.g. transient `bd` invocation during agent
  startup races, or a stale Unix socket). If `bd` crashes or its
  parent exits before tearing down the server, the dolt process is
  reparented to PID 1 and lives forever.
- **Fix**: Implemented `gt dolt zap-orphans`

    - **PRESERVE** if `--port=3307` is in the cmdline.
    - **PRESERVE** if PPID is a live `bd`/`gt`/`gt-agent` process
      (actively in use).
    - **KILL** otherwise (orphan; safe to terminate). Uses SIGTERM
      then SIGKILL with a 2s window via `killSafely`.
- **Test coverage**: `internal/cmd/dolt_zap_orphans_test.go` —
  12 cases for `classifyDoltProc` (canonical PID, canonical port,
  active parent of each managed type, reparented-to-init, unknown
  parent), 7 cases for `parsePortFromCmdline`.
- **Integration**:
    - `internal/templates/roles/mechanic.md.tmpl` — `CMD: gt dolt
      zap-orphans` is now **step 1** of every mechanic patrol cycle.
      Mission text and example conversation updated.
    - `internal/formula/formulas/mol-mechanic-patrol.formula.toml` —
      added `zap-orphan-dolts` step between `check-hook` and
      `scan-logs`. Formula description lists `gt dolt zap-orphans`

### Fix #101 — HQ `issue_prefix` not seeded after a nuclear wipe
- **Symptom**: After `clean-gastown.sh --force ~/gt` (full nuclear
  reset) and a fresh `gt up`, every `gt mail send <hq-target>`
  (mayor/, planner/, deacon/, hq/* polecats) fails with:

      Error: database not initialized: issue_prefix config is
      missing (run 'bd init --prefix <prefix>' for a new project,
      or 'bd bootstrap' to clone an existing remote)

  This blocks the Mayor → Architect → Planner → Polecat → QA
  pipeline at the very first hop: the e2e test script never even
  gets past `[2] Sending project to Mayor...` because the first
  HQ-bound send dies, and any architect that does manage to do real
  work (e.g. by being kicked off via SPEC.md auto-pour from the
  formula engine) can write `architecture.md` but can't notify
  mayor that it's done.

  Concretely seen on 2026-05-12: testgt2 architect produced a
  correct 16-line architecture.md for the FizzBuzz spec at 15:26,
  then looped on `gt mail send mayor/ -s "Architecture Ready"`
  until the prefix row was inserted by hand at 15:33.

- **Root cause**: `gt rig add <name> <url>` runs
  `bd init --prefix <p> --database <name>` for each freshly-cloned
  rig database. That call:
    1. Creates `<rig>/.beads/config.yaml` with `prefix:`/`issue-prefix:`
    2. Runs the bd schema migrations against the rig's Dolt DB
    3. **Inserts the `issue_prefix=<p>` row into `<rig>.config`**

  But there is no equivalent bootstrap step for the **HQ Dolt
  database**. The HQ DB is brought to life implicitly the first
  time the daemon connects to the Dolt server, and `gt up` does
  not call `bd init --prefix hq` for it. After a nuclear wipe

### Fix #104 — Architect template loses the project bead on the
###            mail-driven path

Discovered while validating Fix #102 + #103: even when the test
sends the architect a mail whose body explicitly contains

    Project bead: hq-15v
    Rig: testgt2
    Spec: /home/stevef/gt/testgt2/mayor/rig/SPEC.md
    ...

the architect's LLM cycle does the right design work (reads SPEC.md
from the canonical location, writes a 504-byte architecture.md,
mirrors it to the rig root) — but its handoff mail to mayor is
**still**:

    From: testgt2/architect
    To: mayor/
    Subject: Architecture Ready
    Body:
    Project bead:
    Design complete. architecture.md at ...

i.e. the `Project bead:` line ends at the colon with no ID. This
is exactly the same failure mode as Fix #102's original symptom
(`gt hook | grep -oE 'hq-wisp-...'` returning empty because the
hook is empty), but on a different code path.

**Root cause**: the architect template (`architect.md.tmpl`)
currently scripts the handoff-mail step as:

    gt hook | grep -oE 'hq-wisp-[a-z0-9]+|hq-[a-z0-9]+' | head -1
    → ${PROJECT_BEAD}
    gt mail send mayor/ -s "Architecture Ready" -m "Project bead:
    ${PROJECT_BEAD}\nDesign complete..."

It only looks at `gt hook`. There is no instruction to:
  - check `gt mail inbox` for the assigning mail,
  - extract `Project bead: <id>` from that mail's body if hook
    is empty.

So as long as the architect is woken via mail (not via sling), the
project bead is silently lost on every cycle. Mayor then can't
route the next stage.

**Fix** (template-level, not yet implemented):

  Extend the architect handoff step to a two-tier lookup:

    PROJECT_BEAD=$(gt hook 2>/dev/null \
        | grep -oE 'hq-wisp-[a-z0-9]+|hq-[a-z0-9]+' | head -1)
    if [[ -z "$PROJECT_BEAD" ]]; then
        # Fallback: most recent unread mail with Project bead:
        PROJECT_BEAD=$(gt mail inbox --unread --json 2>/dev/null \
            | jq -r '.messages[].id' \
            | while read mid; do
                gt mail read "$mid" 2>/dev/null \
                  | grep -oE 'Project bead:[[:space:]]*[a-z0-9-]+' \
                  | head -1 | awk '{print $NF}'
              done | head -1)
    fi
    if [[ -z "$PROJECT_BEAD" ]]; then
        # No bead anywhere — BLOCKED, don't send a half-finished mail
        gt mail send mayor/ -s "BLOCKED: no project bead" -m \\
            "Could not determine project bead from hook or inbox."
        exit
    fi
    gt mail send mayor/ -s "Architecture Ready" -m \\
        "Project bead: $PROJECT_BEAD"$'\n'"Design complete..."

The same fallback should be added to the planner template (it
calls itself idle when its hook is empty, but if mayor slung it
with `--on <bead>` correctly the hook will populate; the fallback
covers the mail-only path symmetrically with architect's).

**Status**: REPORTED. The template lives in
`internal/templates/roles/architect.md.tmpl`. Implementing the
fallback is straightforward but requires Go rebuild + reinstall
to ship, so deferred to the next session.

### Fix #109 — Templates used bash-only syntax in /bin/sh

- **Symptom**: After cleanest possible kickoff, the architect
  wrote architecture.md (good!) but the Mayor → Planner handoff
  never happened. Tracing through the architect's session log,
  Step 5's project-bead lookup snippet died with
  `/bin/sh: 1: Syntax error: redirection unexpected`. The bead
  was empty; the architect then tried `bd bootstrap` (cargo cult)
  and stopped — never sent "Architecture Ready" with a valid
  `Project bead:` line, so Mayor had nothing to route on for
  Stage 2.

- **Root cause**: Fix #104 added a two-tier lookup that used
  `while read -r mid; do ...; done < <(gt mail inbox | grep ...)`.
  That `done < <(...)` construct is **bash process substitution**,
  not POSIX. Each `CMD: ...` line from the agent is executed via
  `/bin/sh`, which on Debian/Ubuntu is `dash`. `dash` rejects
  `< <(...)` outright. Both `architect.md.tmpl` Step 5 and
  `planner.md.tmpl` Step 6 had the same bug (they were written
  symmetrically).

- **Fix**: Rewrote the loop to use POSIX-portable
  `for mid in $(gt mail inbox 2>/dev/null | grep -oE 'hq-wisp-[a-z0-9]+' | head -20); do ...; done`.
  Word-splitting on whitespace is fine for our wisp IDs.
  Also added an inline note at the top of each snippet warning
  template editors not to use `done < <(...)` or `[[ ]]` since
  the agent shell is dash, not bash.

- **Validation**: After rebuild, the architect's session log
  should show the lookup succeeding (`project bead: hq-wisp-XXXX`)
  and a real `gt mail send mayor/ -s "Architecture Ready"` with
  a non-empty `Project bead:` line.

  child task beads with the `hq-` prefix instead of the rig prefix
  (`te-` for `testgt2`). Polecats live in the rig; they cannot route
  to or claim `hq-*` work items, so Mayor's polecat fan-out silently
  produced nothing the polecats could pick up.

- **Why "should planner be top-level" is the wrong question**: The
  user asked whether the planner should be town-level rather than
  rig-level, and the answer is yes — it already is, and that's
  correct (multi-rig planning, sees the project bead in Mayor's
  scope, isn't bound to a single codebase). The bug is purely about
  where `bd create` is called from. `bd` does prefix routing by
  walking up from cwd to the nearest `.beads/`; from town-level cwd
  that is always the HQ database.

- **Why `--repo` doesn't help**: `bd create --repo <rig>` is
  documented as "Target repository for issue (overrides
  auto-routing)" but was empirically verified to still emit `hq-*`
  IDs when invoked from town cwd in this build. The only reliable
  way to force the rig prefix is to `cd $TOWN_ROOT/<RIG>` first.

- **Fix (template-only, no Go change required)**:
  In `internal/templates/roles/planner.md.tmpl`:
    * Added new **Step 3a** instructing the planner to derive
      `TARGET_RIG` from the assigning mail / bead description /
      single-rig fallback (`jq -r '.rigs | keys[0]' rigs.json`),
      set `RIG_DIR=$TOWN_ROOT/$TARGET_RIG`, and run **every**
      child `bd create` as `cd "$RIG_DIR" && bd create ...`.
    * Added an inline sanity check: the first created child MUST
      have a non-`hq-` ID; otherwise the cd was skipped and the
      children are useless to polecats.
    * Updated Step 6 so `CHILD_BEADS` enumeration also runs from
      `$RIG_DIR` (`cd "$RIG_DIR" && bd list --parent ...`), and so
      the "Plan Complete" handoff mail carries `Rig: $TARGET_RIG`
      and tells Mayor to enumerate via
      `cd $RIG_DIR && bd list --parent $PROJECT_BEAD`.

- **Why this is not a Go-level fix**: `bd` has no
  rig-scope-by-flag mode that we can rely on (`--repo` is broken
  per the test above). The clean architectural fix would be to
  add `bd create --rig <name>` that resolves via `routes.jsonl`,
  but that's a `bd` change, not a `gt` change. The template
  workaround is correct in the meantime and matches how every
  other rig-scoped operation already routes.

- **Validation plan**: After rebuild + nuclear reset, run
  `e2e_workflow_test.sh`. Expected:
    1. Architect handoff carries `Project bead: hq-...`. (Fix #104)
    2. Mayor slings planner.
    3. Planner cd's into `testgt2/`, creates child beads with
       `te-*` IDs, mails "Plan Complete" with `Rig: testgt2`
       and a `Child task beads: te-...` line.
    4. Mayor's polecat fan-out picks up rig-scoped `te-*` beads
       and slings them to polecats; polecats produce real code
       artifacts in the rig working tree.

### Fix #111 — QA agent copy-pasted its template's example command, flooding Mayor

- **Symptom**: After a nuclear reset and a `gt up`, the testgt2/qa
  agent began emitting one or two new mails per patrol cycle to
  `mayor/` even though it had zero work hooked and an empty inbox.
  Mail subjects were always exactly `QA Complete`, with a body of
  exactly `Review finished for project`. Mayor's inbox accumulated
  3+ of these in the first minute after restart, and Mayor's LLM
  then mis-routed them as Stage 4 (review) signals, drowning the
  fresh Stage 0 kickoff mail.

- **Root cause**: The original `internal/templates/roles/qa.md.tmpl`
  was 22 lines long and had **no idle / no-work branch**. The only
  workflow it described was STARTUP → HOOK → REVIEW → VOTE → COMPLETE.
  Worse, the COMPLETE step contained a **verbatim runnable example**:

      `gt mail send mayor/ -s "QA Complete" -m "Review finished for project"`

  Local LLMs (especially `ollama/llama3.3`) pattern-match on the
  most prominent CMD-shaped string in their prompt. When QA woke
  up on a patrol with no hook and no inbox, the LLM's "what should
  I do?" output was effectively "the most concrete command in the
  prompt" — i.e. copy-paste that example literally. Symptoms then
  cascaded: each cycle produced another `QA Complete` mail to
  Mayor, which contaminated Mayor's inbox, which confused Mayor's
  LLM, which then bypassed Stage 0 entirely.

- **Fix (template-only, no Go change required)**:
  Rewrote `internal/templates/roles/qa.md.tmpl` end-to-end:
    * Added a `⚠️ FIRST: Idle check` section at the very top:
      `gt hook` → if nothing hooked AND `gt mail inbox` is empty,
      output `DONE: idle` and STOP. Explicit forbid-list: do NOT
      run any `gt mail send`, `gt nudge`, `gt qa approve`,
      `gt qa defect`. "Idle means do nothing — not 'report idle
      to mayor'. Mayor patrols its own inbox; it does not need a
      heartbeat from QA."
    * Replaced the literal-runnable example with a heredoc that
      requires a `$BEAD` shell variable populated from `gt hook`:

          gt mail send mayor/ -s "QA Complete" --stdin <<MAIL
          Project bead: $BEAD
          Verdict: pass   # or "fail"
          Review finished. See bead $BEAD for details.
          MAIL

      Annotated with: "A bare `Review finished for project` is a
      placeholder — never send it verbatim. If `$BEAD` is empty
      you are not actually reviewing anything; go back to step 1."
    * Added POSIX-shell warning (no `[[`, no `< <(...)`) for
      consistency with Fix #109.

- **Validation observed in same session**:
  After rebuild + `gt down`/`gt up`, the testgt2/qa session log
  shows the LLM did try the new heredoc form on its first post-
  Fix-#111 patrol, but emitted it as a single concatenated line
  (`<<MAIL Project bead: $BEAD ... MAIL`). The agent runtime
  correctly classified this as malformed and ran `true` instead,
  so **zero spam mails were sent**. Defence-in-depth working as
  intended: even if the LLM tries something dumb, the runtime
  rejects it. A future Fix #113 may further constrain the
  heredoc-on-one-line failure mode, but it's currently a no-op,
  not a regression.

### Fix #112 — Mayor LLM hallucinates "Stage N complete" without running the stage

- **Symptom**: With a pristine HQ inbox containing exactly one
  unread mail (`Project: build FizzBuzz for testgt2`, our Stage 0
  kickoff), Mayor's LLM (`ollama/llama3.3`) on its very first
  post-nudge patrol turn:
    1. Ignored the new mail entirely.
    2. Issued six `gt mail read <id>` commands for mail IDs that
       were NOT in the current inbox view (they referred to
       previously soft-cleared beads).
    3. Tried `gt sling mol-idea-to-plan --on $(gt mail read ... | grep -oE 'hq-wisp-...' | head -1) planner`
       — i.e. command substitution inside a sling arg, which the
       runtime correctly rejected as a "hallucinatory sling".
    4. Then emitted `gt mail send --self -s "Stage 2 complete"
       -m "Planning stage complete for project hq-wisp-ct8.
       Ready for implementation."` despite never having run a
       single `bd create` or `gt sling` to a planner.

  Net effect: Stage 0 was bypassed. The kickoff mail was never
  even read. Mayor lied to itself that planning was done.

- **Root cause (template + LLM, NOT a Go bug)**:
  The original mayor.md.tmpl described the routing table well but
  did not enforce a **deterministic per-cycle entry point** or a
  **truth-condition for "Stage N complete" self-mails**. Combined
  with a weak local LLM that pattern-matched on stale mail IDs
  from prior cycles (visible in the bead store even after
  `gt mail clear`, which only soft-acknowledges), Mayor invented
  state transitions that never happened.

- **Fix (template-only, no Go change required)**:
  Inserted a new `## CRITICAL RULES (Fix #112)` block immediately
  after `## YOUR ONE JOB` in `internal/templates/roles/mayor.md.tmpl`,
  with five mechanical rules the LLM must follow before any other
  action:

    1. **STEP 1 IS ALWAYS `gt mail inbox --unread`.** Forbid
       reading any specific mail id until the current unread
       listing has been observed. Mail ids from prior patrols
       are treated as stale and must not be invented from memory.
    2. **Process the OLDEST unread mail first, ONE AT A TIME.**
       Pick the bottom of the listing. Read ONLY that mail.
       Classify by `Subject:`. Run exactly one routing command
       (or the Stage 0 atomic pipeline). Then STOP.
    3. **Never fabricate "Stage N complete" self-mails.** A
       self-mail saying a stage was completed is only valid AFTER
       a corresponding `gt sling` or `bd create` succeeded in
       this same cycle.
    4. **No command substitution inside `gt sling` args.** If a
       bead id is needed, transcribe it as a literal in a
       follow-up command, or use Stage 0's `sh -c '...'` pattern
       for variable passing.
    5. **Stale mail rule.** If a later-stage signal carries an
       empty `Project bead:` line or a bead id that `bd show`
       cannot find, run `gt mail delete <mail-id>` and continue
       to the next unread; do NOT route a stale signal.

- **Why this is not "just upgrade the LLM"**: The user can swap
  the Mayor LLM at any time, but Gas Town claims to be runnable
  on local models. The template should make the routing path
  hard to mis-execute regardless of LLM strength. The CRITICAL
  RULES block also serves as a clear failure narrative for the
  next debugging session: if Mayor still fabricates completions,
  we know the LLM is too weak and an upgrade is the next lever.

- **Validation plan**: After rebuild + most-aggressive cleanup
  (gt down → kill stragglers → nuclear `clean-gastown.sh --force`
  → wipe `.dolt-data/` → bd-delete every leftover mail bead →
  reset `gt-agent-state.json` for every agent → gt up → seed HQ
  prefix → re-add testgt2 → gt up → send Mayor a human-style
  kickoff mail), monitor the Mayor session log. Expected first
  LLM output of patrol #1:
    `CMD: gt mail inbox --unread`
  followed by reading exactly the single fresh project mail,
  followed by the Stage 0 atomic `sh -c '...'` pipeline. Any
  deviation (reading a stale id, emitting "Stage 2 complete"
  without running `gt sling`, etc.) means either the template
  is still under-specified OR the local LLM is too weak — at
  that point, swap to a remote LLM as the next debugging lever.

### Fix #113 — Mayor Stage 0 `sh -c '...'` pipeline keeps erroring out

- **Symptom**: With every fix above in place and a freshly nuked
  town, Mayor still failed at Stage 0 every kickoff with one of:
    1. `Syntax error: Unterminated quoted string` at "line 11" of
       the `sh -c '...'` body.
    2. `Syntax error: "then" unexpected` on the first line of
       the body.
    3. `SyntaxError: invalid syntax` inside an inner
       `python3 -c "..."` invocation.
  Each shape produced a `BLOCKED: bd create failed` self-mail and
  Stage 0 never created the project bead, so the pipeline stayed
  parked at Stage 0 forever.

- **Three independent root causes, one observed regression**:

  - **Cause A (parser): blank line inside a multi-line CMD: block**
    terminated the captured script early. `parseLLMResponse` in
    `cmd/gt-agent/main.go` used to flush `scriptBuf` on the first
    blank or markdown-shaped line after the `CMD:` marker. Mayor's
    Stage 0 template has paragraph-style blank lines for
    readability inside `sh -c '...'`, so the parser handed sh a
    body whose opening `'` was never closed — hence "Unterminated
    quoted string". Fixed by adding a `hasOpenShellQuote()`
    helper that scans `scriptBuf` for unbalanced `'` / `"` and,
    when the quote is open, treats blank/markdown/prose lines as
    part of the quoted string instead of as script terminators.
    Heredocs continue to be tracked by the existing `heredocTerm`
    state.

  - **Cause B (LLM): collapsing multi-line scripts to a single
    line of whitespace-separated tokens**. The local llama3.3
    sometimes flattens newlines to spaces, turning
    `set -u\nMAIL_ID="..."\nif [ ... ]; then\n  echo ...\nfi`
    into `set -u MAIL_ID="..." if [ ... ]; then echo ... fi`,
    which sh cannot parse. Fixed by rewriting the Stage 0
    pipeline in `internal/templates/roles/mayor.md.tmpl` as one
    logical line of `sh -c '... ; ... ; ... ; ...'` with explicit
    `;` after every statement. The script now works whether the
    LLM keeps newlines or collapses them.

  - **Cause C (runtime): blanket `\"` → `"` unescape destroyed
    nested escapes**. `gt-agent`'s pre-exec normalizer
    unconditionally ran `strings.ReplaceAll(cmd, "\\\"", "\"")` to
    clean up over-escaping from chatty LLMs. That stripped the
    `\"` inside `python3 -c "import json,sys; ... print(d.get(\"id\"))"`,
    which broke sh's double-quote nesting and left the inner
    Python with `print(d.get(id) or d.get(ID) or )`. Fixed by
    adding `isMultilineQuotedScript(cmd)`: when the captured
    command is a multi-line `sh -c '...'` / `bash -c "..."`, skip
    the unescape and let sh do its own escape processing.
    Additionally swapped the Python one-liner in the Stage 0
    pipeline for `jq -r ".id // .ID // empty"` so no inner
    double-quote-in-double-quote escaping is needed in the first
    place.

- **Files**: `cmd/gt-agent/main.go` (parser quote-state tracking,
  `hasOpenShellQuote`, `isMultilineQuotedScript`, exempt from the
  unescape pass), `cmd/gt-agent/main_test.go` (new
  `TestIsMultilineQuotedScript`, three new
  `TestParseLLMResponse` cases),
  `internal/templates/roles/mayor.md.tmpl` (Stage 0 pipeline
  rewritten as a oneliner with `;` separators, SEMICOLON RULE
  added, HEREDOC RULE strengthened, Python replaced with `jq`).

- **Validation**: After rebuild Mayor's patrol #1 emitted the
  oneliner Stage 0 script exactly as expected; sh parsed it
  cleanly; `bd create` returned `hq-9jo`; `gt sling shiny --on
  hq-9jo testgt2/architect` succeeded on the canonical path
  (no mail-fallback needed); Mayor self-mailed `Stage 0 complete:
  hq-9jo` and stopped with `DONE: Stage 0 dispatched`. End-to-
  end Stage 0 now reliably works in a single patrol turn.

### Fix #114 — Mayor fan-out noise + hardcoded rig examples in templates

- **Symptom (after Fix #113 unblocked Stage 0)**: Stage 0 worked,
  Mayor slung `shiny` to the architect — but downstream the
  pipeline still stalled and the inboxes filled with junk:

    1. **Architect never wrote `architecture.md`.** It read the
       SPEC, then drifted onto `gt patrol` / `gt patrol report`
       commands (those are deacon/witness/refinery commands, not
       architect commands) and eventually unhooked itself idle.
    2. **Planner woke up uninvited and mailed BLOCKED.** With no
       `mol-idea-to-plan` sling and an empty inbox, the planner
       still hallucinated work — running `gt patrol output
       archives`, `gt patrol new --portal mol-planner-patrol`
       (made-up flags), then mailing Mayor `BLOCKED: missing
       architecture file` referencing a `mol-planner-patrol`
       proto that does not exist.
    3. **Mayor amplified the noise** by replying to the planner's
       `BLOCKED: missing architecture file` with
       `gt mail send planner/ -s "Investigate BLOCKED:
       missing architecture file" -m "Check canonical locations
       for architecture file and verify mol-planner-patrol for
       details."`, then later mailing the architect
       `gt mail send testgt2/architect -s "Create architecture"
       -m "Please create the architecture file ..."`. The first
       is exactly the "do NOT re-sling the same stage" anti-
       pattern the routing table calls out. The second is even
       worse: the architect was already slung the design step at
       Stage 0 via the canonical `shiny` sling — re-mailing
       "Create architecture" just adds redundant work that the
       architect role template explicitly ignores.

- **Three independent root causes**:

  - **Cause A (formula): `shiny.formula.toml`'s `design` step had a
    hardcoded example baked into the `description`** —
    literally `/home/stevef/gt/testgt2/architect/` AND `Hello API`
    AND a `printf` example for a FastAPI project. The architect's
    LLM saw the kickoff mail (FizzBuzz SPEC) AND the wisp
    description (Hello API printf example) and could not reconcile
    them. This is a direct repeat of Fix #85's "example text in a
    prompt becomes a regurgitation pattern" — the formula was
    written when testgt2 was the only ever-used rig and the
    canonical example accidentally shipped to production. Fixed by
    rewriting the `description` to be spec-agnostic ("Read the
    project SPEC ... write architecture.md following your architect
    role template"). The architect template (`architect.md.tmpl`)
    already has the detailed step-by-step instructions, so the
    formula step just needs to point at it, not duplicate it.

  - **Cause B (templates): hardcoded `testgt2` rig name and
    `/home/stevef/gt` path** scattered through
    `mayor.md.tmpl`, `planner.md.tmpl`, and
    `mol-mechanic-patrol.formula.toml`. The mayor template said
    "For this town the rig is almost always `testgt2`." The
    planner template's `jq` shape example used `testgt2` and its
    "FILE PATH DISCIPLINE" example pasted a literal
    `/home/stevef/gt/testgt2/architect/architecture.md`. The
    mechanic patrol formula's `rig` var had `default = "testgt2"`
    and `town_root` had `default = "/home/stevef/gt"`. All of
    these are dev-machine leakage that will break the moment
    anyone creates a rig with a different name. Fixed by
    replacing `testgt2` with `<rig>` or `<rig-name>` in all
    illustrative text and removing the dev-specific defaults
    (mechanic patrol now `required = true` on those vars; the
    formula consumer must pass them at sling time).

  - **Cause C (runtime): Mayor's fan-out responses to BLOCKED /
    IDLE mails** — the LLM is incapable of stopping at a BLOCKED
    signal. The template already said "investigate, do NOT re-
    sling the same stage" but the LLM routed around it by
    rephrasing: "Investigate BLOCKED: ...", "Check canonical
    locations", "Please create architecture", "RE: IDLE
    Acknowledged". Each of these produces another BLOCKED reply
    from the recipient and a feedback loop builds. Fixed by
    pushing the rule from the template down into
    `hasContentFreeMailSend` in `cmd/gt-agent/main.go`:
      * `mailSendInvestigateForwardRE` rejects subjects like
        `Investigate BLOCKED:`, `Check canonical locations`,
        `Please investigate ...`, `Verify ...`, `Review ...`.
      * `mailSendCreateArchitectureRE` rejects subjects like
        `Create architecture`, `Write architecture.md`,
        `Generate the architecture document`. The architect was
        already slung; re-mailing duplicates the request.
      * `mailSendREIdleRE` rejects `RE: IDLE`, `RE: REPORT: idle`,
        `RE: IDLE: no work` — these are status pings the
        recipient already has, with bodies that are always echo
        acks ("Acknowledged, idle status confirmed.").
    All three guards apply at the gt-agent boundary, so a
    misbehaving LLM cannot bypass them by reshaping the prose.

- **Template changes for defence-in-depth**: Added a Critical
  Rule #6 and #7 to `mayor.md.tmpl`: "DO NOT FAN OUT NOISE"
  (explicitly forbids the three observed patterns by example) and
  "DO NOT FAKE-SLING TO THE PLANNER" (the planner is woken only
  by `gt sling mol-idea-to-plan`). Also strengthened the routing
  table: `BLOCKED:` mail → `gt mail delete <id>` and stop, do
  NOT re-mail anyone. `IDLE` / `REPORT: idle` mail → same.

- **Files**: `cmd/gt-agent/main.go` (three new regexes,
  three new `hasContentFreeMailSend` branches),
  `cmd/gt-agent/main_test.go` (nine new test cases covering all
  three reject patterns and four real-traffic allowed cases that
  must not trip),
  `internal/templates/roles/mayor.md.tmpl` (Critical Rules #6/#7,
  routing table strengthened, `testgt2`-hardcoded line removed),
  `internal/templates/roles/planner.md.tmpl` (three `testgt2`
  illustrative-text replacements with `<rig>` / `<rig-name>`),
  `internal/formula/formulas/shiny.formula.toml` (design step
  description rewritten spec-agnostic),
  `internal/formula/formulas/mol-mechanic-patrol.formula.toml`
  (dev-specific `default = "testgt2"` / `default = "/home/stevef/gt"`
  replaced with `required = true`).

- **Why this is a worth-recording fix rather than "the LLM is
  just bad"**: The hardcoded `testgt2` / `Hello API` content
  would break for ANY new rig name even with a much stronger
  LLM. Gas Town is supposed to be rig-agnostic; the templates
  and formulas have to be too. The fan-out guards are
  belt-and-braces defence so the system continues to make
  forward progress even when the LLM regresses on the rule.

- **Validation plan (next session)**: Single-mail kickoff with
  fresh nuclear reset. Expected sequence: Mayor Stage 0 →
  shiny sling → architect reads SPEC → architect writes
  architecture.md → architect mails `Architecture Ready` with
  `Project bead:` → Mayor slings `mol-idea-to-plan` to planner
  → planner creates rig-scoped child beads → Mayor slings
  `mol-polecat-work` per task. No `Investigate BLOCKED` mails,
  no `Create architecture` mails, no `RE: IDLE` mails should
  appear anywhere in the logs. Any of these surfacing means
  the LLM found a new phrasing that escapes the regexes; in
  that case extend the regexes and re-record under Fix #114b.

## Open Issues (next session)

### Auto-save misroute mitigation (see Fix #99)

The auto-save commit guard inside `internal/cmd/done.go` still
unconditionally commits to whatever `cwd` is current when there are
uncommitted changes. Long-term we need one of:

- A worktree-shape guard ("am I sitting in a rig worktree?")
- A `GT_NO_AUTOSAVE=1` env opt-out for development shells
- An audit of the call sites that can reach `gt done` with a
  non-rig cwd

Until then, do NOT run `gt done` while your shell is parked inside
the gastown source repo, and check `git log -1 --format='%an %ae'`
before pushing if you're not sure.

/ `Patrol Cycle #N`" issue is **substantially resolved** by Fix 90
(extension) and Fix 92 — the `gt-agent` normalizer now rejects those
mails at the source. The remaining tail (a small number of legitimate
